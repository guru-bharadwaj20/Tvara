# Matched CPU baseline

Clone `https://github.com/ggml-org/llama.cpp.git` into `_work/llama.cpp` and check out `45451c366d4256f94fbc8845645e31a6b9155054`. Run `python tools/pin_benchmark_models.py`, then `python tools/run_matched_baseline.py` after building the native Release library. Debug fallback is rejected and the native binary hash is recorded. The driver adds a small CMake target in the ignored source checkout, leaving llama.cpp kernels unchanged. It reuses the Release build directory and records the exact revision.

Both engines load the same checksum-pinned F32 or Q8_0 random-weight tiny Llama GGUF file. The shared model uses interleaved RoPE. Prefill uses token IDs 1 through 16; decode continues with 17 through 24. Both engines compute full vocabulary logits at every position, including all prefill positions. CPU inference uses one thread and no GPU. One warmup and five measured repetitions exclude model loading; native sequence allocation is also outside each timed interval. Native prefill executes token by token; llama.cpp submits one prompt batch. The baseline emits independent final-prefill logits and the F32 comparison must meet atol 1e-5 / rtol 1e-4 before results are recorded.

Native Q8_0 weights currently dequantize to F32 on loading. llama.cpp keeps quantized matrices and may quantize activations, so Q8 arithmetic and kernel costs differ. The native timings include ctypes calls and output-buffer allocation. This tiny random fixture establishes reproducibility and regression evidence; it cannot establish trained-model quality, representative large-model throughput, or production acceleration. Temperature, clock frequency and background load are uncontrolled.
